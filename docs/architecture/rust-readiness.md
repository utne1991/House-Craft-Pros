# Rust readiness — evaluation + benchmark (Sprint 01, T025/T028)

**Status: benchmark COMPLETE.** TypeScript vs Rust measured under benchmark
parity on 25/11/2026. Recommendation: **stay on TypeScript for Sprint 01
and the next sprints; Rust is not needed at ~44k licenses.** The numbers
below are the evidence; the conditions under which that answer would change
are in §5.

## 1. Environment (measured 25/11/2026)

| Item | Value |
|---|---|
| Machine | 4 CPUs, 7,934 MB RAM, Linux 7.0.0-44-generic x86_64 |
| Node | v24.22.1 |
| Rust | rustc 1.100.0 (0ef1bc386 2026-11-09), cargo 1.100.0 — installed 25/11/2026 via official rustup (rust-lang.org); `cargo`/`rustc` were absent before that |

## 2. What was benchmarked (parity rules)

- **Same CSV files** (same SHA-256, recorded in each `summary.json`).
- **Same machine**, same normalization + dedupe rules, same output schema
  (canonical `records.jsonl` / `businesses.json` / `dedupe.json`).
- **Scope: parse + normalize + dedupe only** — the CPU-bound stages. The
  Rust harness (`etl/bench/rust-harness/`, std-only, no crates) builds **no
  database loader** by design (no Rust engine in this sprint), so DB write
  speed is measured for the TypeScript production path only (§4).
- Each side ran **3 times**; medians are reported. Raw summaries:
  `/tmp/hcp-bench-out/{ts,rs}/run{1,2,3}/summary.json` (kept out of the
  repo — the canonical outputs contain real licensee PII). The report is
  generated by `etl/bench/run-bench.sh` → `etl/bench/results-2026-11-25.md`.

## 3. Results (median of 3 runs, 43,976 licenses)

Figures are medians of 3 runs (the middle value), not best-of-3. (Correction
25/11/2026 after independent QA finding F1: an earlier draft reported the
minimum of the 3 runs as the "median".)

| Metric | TypeScript (Node 24) | Rust 1.100.0 (release) |
|---|---|---|
| End-to-end wall time | **2,715 ms** | 3,227 ms |
| User CPU | 2,900.8 ms | 3,020.0 ms |
| System CPU | 484.3 ms | 180.0 ms |
| Peak RSS | 708 MB | **196 MB** |

Per-run detail: TS wall 2,715 / 2,674 / 2,737 ms; Rust wall 3,308 / 3,227 /
3,204 ms. TS RSS 662 / 710 / 708 MB; Rust RSS 196 MB in all three runs.

### Output accuracy — byte-identical, zero unexplained deltas

All three canonical outputs are **byte-identical** between the two builds
(run1), and stable across runs per side:

| File | SHA-256 (first 16 hex) | Rows |
|---|---|---|
| `records.jsonl` | `b1989c6c522f9cf9…` | 43,976 records |
| `businesses.json` | `01188dd7b8323e32…` | 43,895 businesses |
| `dedupe.json` | `047c4ec39a39bd46…` | 78 merged + 1,355 held decisions |

Counts agree with the production dry-run: 40,190 active / 3,786 expired /
0 unknown. (The bench's 43,895 businesses vs the DB's 43,837 is the
loader's cross-source business reuse — 58 further merges by the same
evidence rule — not a benchmark difference; both bench sides agree.)

**One delta was found and fixed during the run, not papered over:** the
first comparison differed in exactly 1 of 43,976 records — city
`"GRAND  PRAIRIE"` (double space in the source CSV). The TypeScript
normalizer preserves the source spelling verbatim; the first Rust version
collapsed internal whitespace (`split_whitespace().join(" ")`). The Rust
harness was fixed to preserve the source text, and the outputs then matched
byte-for-byte. No other delta exists.

## 4. DB write speed

TypeScript production path only (psql COPY + upsert, one transaction per
source, from the 25/11 dry-run, wall time including ~2 s download each):
RMP 9,412 rows ~6 s end-to-end; electrical 14,066 rows ~9 s; HVAC 20,498
rows ~10 s. **Rust DB write was NOT measured** — the harness has no loader,
and no number is claimed for it. Any future Rust loader must be measured
the same way (same files, same machine, same transaction shape) before any
claim is made about it.

## 5. Evaluation and conditional recommendation

**TypeScript is good enough at ~44k licenses, and the numbers say so:**

- The whole parse + normalize + dedupe pass takes ~2.7 s; a full
  per-source load (download + parse + normalize + dedupe + DB write)
  takes ~6–10 s. Daily refreshes of three Texas sources are minutes of
  work, not hours.
- Rust is **not faster here**: 3.2 s wall vs 2.7 s for Node, with nearly
  identical user CPU. The Rust advantage at this scale is **memory**
  (196 MB vs 708 MB, 3.6× less) and system CPU (180 ms vs 484 ms) — real,
  but not a reason to rewrite a working engine.
- The TypeScript RSS (708 MB) comes from holding all records plus the
  canonical JSON strings in memory. If memory ever matters, streaming the
  JSONL output would cut it without a language change.

**Conditions under which Rust would win — re-benchmark then:**

1. **Volume grows ~10–100×** (multi-state ingestion, or daily loads of
   several hundred thousand licenses): re-run the same parity harness on
   the larger files. Rust's memory advantage compounds there; wall time
   may flip once Node's GC pressure dominates.
2. **A memory-constrained runner** (e.g. a small CI worker or a
   memory-capped container) where 708 MB is a real limit, not a comfort
   number.
3. **A Rust loader exists and is measured**: DB write speed is the one
   metric this benchmark did not cover for Rust. A future Rust engine
   would need a real Postgres loader (a `postgres` crate, or the same
   psql bridge) and must re-prove output parity byte-for-byte, the way
   this harness did, before it replaces anything.

**Decision:** one production engine — TypeScript (`etl/src/`). The Rust
harness stays in `etl/bench/` as a benchmark only, never in the production
run path. No conclusion by speculation: if any of the three conditions
above is met, re-run `etl/bench/run-bench.sh` on the new workload and let
the numbers decide.
